## Design Specificity Verdict

**A generic B2B admin template with a genuine pharmacy spine grafted on.** The shell plus roughly 14 of ~34 screens are category-interchangeable; the PDV, Precificador, Receitas and Rastreabilidade flows are authored for this business.

**LLM assessment (unanchored):** The skeleton is textbook SaaS admin — 264px left rail with 9 labelled groups + collapse toggle, sticky 60px topbar with search/bell/settings, `max-width:1480px` content, per-page eyebrow/title/desc header. `CrudPage` is a literal generic factory (PageHead + stat row + card-wrapped table + eye/pencil/trash + create/edit modal + detail drawer) reused unchanged across Equipe, Produtos, Marcas, Categorias, Serviços, Classe Terapêutica, Localizações, Fornecedores, Lojas, Cupons, Promoções, Áreas e Frete and more — fourteen screens, one skeleton. `StatCard` is the canonical KPI card. The icon set is a generic line family and the "brand mark" is just the `rx` clipboard glyph in a white square, reused as the Receitas nav icon. Nothing in the layout, motion or interaction model says "pharmacy" — swap the copy and it's an ERP.

Where it *is* authored: `useAtendimento` models a real balcão with separate farmacêutico and caixa screens sharing a cart through an explicit handoff queue, and `rxOk` genuinely **disables "Gerar nota fiscal"** until every controlled line is bound to a prescription — the rule lives in state, not just a label. The domain vocabulary is load-bearing, not decoration. `calcPricing` is real dual-channel margin modelling (imposto, rateio de aluguel, comissão do marketplace, taxa de pagamento, desconto PIX, frete → live loja vs marketplace margin + repasse líquido + prejuízo alert). `RecorrenciaBox` turns CRM data into a counter action with a next-cycle date and "ciclo atrasado há N dias".

So: not interchangeable *overall*, but the surfaces a user touches most — nav, dashboard, every cadastro screen — are template-grade, and the red paint doesn't change that.

**Deterministic scan (`detect.mjs --json`):** Exit 2, but **DEGRADED** — the HTML/CSS AST modules (htmlparser2, css-select, css-tree, domutils) were unavailable, so it fell back to regex and did not evaluate custom properties, selector matching or computed contrast. Treat its output as a floor. **1 finding:** `layout-transition` at line 71 — `.rail { transition: width .22s }` animates a layout property. The regex pass missed two sibling cases: `@keyframes printing-fill` animating `width:0%→100%` (line 337) and `.switch .knob { transition:left }` (line 243). `detect-csp.mjs` ran clean but does not check external-script blocking, so it gave no signal on the CSP failure below.

**Visual overlays:** none — no browser automation tool was exposed, so injection, screenshots and the `[Human]` overlay tab were all skipped. Every tap-target and contrast number below is computed from source, not measured from a rendered layout.

## Overall Impression

There is real domain intelligence here — the controlled-substance gate, the pharmacist→cashier handoff, the dual-channel pricer, the recurrence prompt. Someone who knows how a Brazilian pharmacy actually runs shaped the hard parts. But that intelligence is wrapped in a generic admin shell that fails the actual usage scene: a rushed, interrupted user at a counter, often on a mid-size screen, doing legally-consequential things. The single biggest opportunity is to **make friction match stakes** — right now deleting a store record, approving a controlled-substance prescription and issuing a fiscal note all cost exactly one unconfirmed click, while the Precificador demands 16 fields up front. Second: the app already knows the user's role but refuses to use it as the organizing principle.

And one hard blocker sits underneath all of it (see P0 #1): as published, the artifact almost certainly renders a blank page in the claude.ai sandbox.

## What's Working

1. **The PDV two-persona model is authored for a real counter, and the state machine enforces it.** `useAtendimento` splits farmacêutico and caixa into separate screens that share a cart only through an explicit handoff queue (`enviarParaCaixa` / `pickupHandoff`), and `rxOk` disables the finish button until every controlled line is tied to a prescription link or a physically-presented script. The rule is enforced in state, not just displayed — this mirrors how pharmacist judgement and cashier transaction are genuinely separated at the balcão.
2. **The client context panel + `RecorrenciaBox` put CRM data where the conversation happens.** Birthday, children, continuous-use meds, purchase-history chips, cashback and a computed "atrasado para recompra" flag render right next to the cart; the recurrence editor computes the next cycle date and flags "ciclo atrasado há N dias". It's a next-best-action at the moment of service, not a buried report.
3. **The Precificador models the real cost stack of a dual-channel pharmacy.** `calcPricing` separates loja física from marketplace and folds in impostos, rateio de aluguel, comissão, taxa de pagamento, desconto PIX and frete, showing live margin for both channels plus repasse líquido and a negative-margin alert. Domain-specific financial reasoning, not a price field.
4. *(Craft)* One consistent 20px hand-drawn icon set at a single stroke width; a full `prefers-color-scheme: dark` token set with a matching `[data-theme]` override; a global `prefers-reduced-motion` guard.

## Priority Issues

### [P0] The published artifact renders blank in the claude.ai sandbox
- **What:** Lines 351–353 load React, ReactDOM and babel-standalone from `cdnjs.cloudflare.com`, and the bootstrap (lines 4724–4731) runs `Babel.transform(...)` at runtime on the app source. The Claude-artifact CSP blocks all external hosts except Google Fonts, so all three script requests are refused → `React` / `ReactDOM` / `Babel` are `undefined` → the bootstrap throws → `#root` stays empty.
- **Why it matters:** Whatever the design merits, nobody can use it. This is a total functional failure in the real environment, not a nitpick.
- **Fix:** Inline React + ReactDOM production UMD builds directly into the file (or drop React and author in plain DOM/another approach), and **precompile the JSX at build time** — remove babel-standalone and the runtime `Babel.transform` entirely. Nothing but Google Fonts may be fetched cross-origin.
- **Suggested command:** `/impeccable optimize`

### [P0] Irreversible, legally-consequential actions have zero friction
- **What:** Every CRUD table's trash icon calls `removeRow` instantly — no confirm, no undo, no toast. "Emitir nota" (fiscal document), prescription "Aprovar", and order-step "Avançar" are each one unrecoverable click. Modals and drawers don't close on Escape and don't restore focus, so there isn't even a calm exit.
- **Why it matters:** The usage scene is interrupted and rushed. This will cause real record loss and mis-issued fiscal documents, and a mis-tapped controlled-substance approval carries legal exposure for the pharmacist. The detector and design review agree the app has essentially no "emergency exit."
- **Fix:** Confirm dialog naming the entity + a 5–10s undo toast for deletes; a preview/confirm sheet before nota emission; a checkbox affirmation ("Conferi prescritor, posologia e validade") before approving controlled prescriptions; a "voltar etapa" on the order stepper; Escape closes overlays and returns focus.
- **Suggested command:** `/impeccable harden`

### [P1] The rail is 37 destinations in 9 always-open groups, with no role scoping and a dead global search
- **What:** `NAV_GROUPS` renders every item for every user. The app models Admin / Gerente / Farmacêutico / Caixa, yet a cashier scrolls past Custo de Construção, Precificador, Áreas e Frete and Auditoria to reach the PDV. The topbar search is wired to `value="" onChange={()=>{}}` — pure decoration.
- **Why it matters:** Navigation is the user's constant cost. 30+ irrelevant links per shift is pure extraneous load and defeats scanability — the core promise of an Operate surface.
- **Fix:** Role-based nav filtering tied to the real signed-in user (not the fake dashboard pill); collapsible, persisted groups; a pinned/frequent section; turn the dead search into a working Cmd-K command palette that jumps to any page or entity.
- **Suggested command:** `/impeccable distill` (plus `/impeccable clarify` for the role model)

### [P1] The accessibility floor is effectively absent
- **What:** Zero `:focus-visible` in the file; no focus ring on `.btn`, `.icon-btn`, `.rail-item`, `.tab`, `tr.clickable`, and the topbar search input has `outline:none` with no `:focus-within`. Primary nav items, tabs and clickable table rows are `<div onClick>` / `<tr onClick>` with no `tabIndex`/`role`/`onKeyDown` — only 2 keyboard handlers exist in the whole app (both "Enter" on a text input). Zero `role=`, zero `aria-*`, zero `<nav>`/`<main>`/`<header>` landmarks; `<html>` has no `lang`; `SwitchToggle` is a non-focusable `<div>`; modals have no `role="dialog"`/`aria-modal`/focus trap. Icon-only recurrence steppers are 22×22px (below the 24px AA floor); `.icon-btn` is 34×34.
- **Why it matters:** Sam (a primary persona for any admin tool) cannot operate this at all, and a sighted keyboard user can't see where focus is. For an internal tool used all day, this is a P1, not polish.
- **Fix:** Semantic elements + `aria-label` on every icon-only control; a visible `:focus-visible` ring on all interactive elements; keyboard path for row actions, tabs and nav; dialog semantics + focus trap + Escape on overlays; `lang="pt-BR"`; bump sub-24px targets.
- **Suggested command:** `/impeccable audit`

### [P1] Responsive behaviour fails the counter-tablet scene
- **What:** Only two breakpoints exist (`max-width:1100px`, `max-width:680px`) and both touch **only** the `.g-5/.g-4/.g-3/.g-2` stat grids. The 264px rail never auto-collapses to a drawer (manual button only). `.pdv-shell` (`1fr 360px`) and the chat grid (`300px 1fr`) never reflow. `.g-12` has no responsive rule and is used 15× with hard-coded `gridColumn:'span 7'/'span 5'` children — at 375px a `span 5` panel is ~100px wide. The main reusable `DataTable` renders a bare `<table>` that is *not* wrapped in the `.table-wrap` overflow container.
- **Why it matters:** Staff on a counter tablet or small laptop get a squeezed PDV, crushed dashboard panels and a page body that scrolls horizontally.
- **Fix:** ≤1200 / ≤900px rules that collapse `span-N` to full width, stack `pdv-shell` and the chat layout, convert the rail to an overlay drawer below a breakpoint, and wrap every table in `.table-wrap`.
- **Suggested command:** `/impeccable adapt`

### [P1] Red is brand, primary, focus ring and danger simultaneously — and the status badges sit at marginal contrast
- **What:** `--accent:#a11017` paints the entire sidebar, primary buttons, links, focus rings and charts; `--critical:#b3261e` is one hue-step away; `.btn-danger` and `.badge-accent` are both pale-red pills. Contrast spot-checks: `.badge-good` text `#2e7d5b` on `#e4f1eb` ≈ **4.3:1 — fails AA** at 11px; `.badge-warning` ≈ 4.68:1 (passes by a hair); 10.5px uppercase `thead th` muted-on-`surface-2` ≈ 4.54:1 (marginal).
- **Why it matters:** Under shop lighting and at a glance, "primary" and "destructive" aren't reliably distinguishable, ambient red drives alarm fatigue that blunts genuine critical badges, and the small status text is at or below the AA line exactly where quick scanning matters.
- **Fix:** Keep red as brand chrome but desaturate/darken the rail; move the primary action to a distinct value; differentiate `--critical` with a border + icon, not just a soft fill; darken the badge text colours (or enlarge/weight the badge text) to clear 4.5:1 with margin.
- **Suggested command:** `/impeccable colorize`

## Persona Red Flags

**Alex (power user):**
- Topbar search is dead — no jump-to-order/client/product, no Cmd-K, no shortcuts anywhere.
- `DataTable` headers don't sort; no multi-select, no bulk delete / bulk status change / bulk prescription approval — every action is a one-at-a-time drawer round-trip.
- No saved views or filters; no pagination or virtualization, so long lists are a manual scroll.
- Store switch (a rail `<div>`) and dashboard role switch (a pill) are two different buried mechanisms for what feels like one concept.

**Sam (accessibility-dependent):**
- Screen reader hears "button" with no name for eye/pencil/trash on every row and for the topbar calendar/bell/sliders.
- `Tabs` aren't in the tab order or announced as a tablist; clickable `<tr>` rows do nothing on Enter; `SwitchToggle` announces nothing and can't be reached by keyboard.
- Modal/Drawer don't trap focus, aren't announced as dialogs, and Escape doesn't close them — focus is stranded behind the overlay.
- No `:focus-visible` anywhere; 10px/700 rail group labels at `rgba(255,255,255,.66)` and pervasive 10–11px muted text are low-contrast.
- Approve / delete / advance produce no announced confirmation.

**"Dani" — plantão pharmacist/cashier, customer waiting at the counter (project-specific):**
- Global search doesn't work, so "the Nogueira order" can't be pulled up fast — must guess the module and scan a table with no sort or pagination.
- ~30 nav links stand between every shift and the PDV; no pin; the collapsed rail is unlabeled icons.
- Approving the waiting customer's controlled script: "Aprovar" sits at equal visual weight beside "Reprovar" in a narrow drawer — a rushed mis-tap approves it, no confirm, no un-approve.
- Order stepper "Avançar" has no undo — hand the wrong bag, advance to "Entregue", stuck.
- Pickup code must be read off the customer and typed while they wait; a wrong entry errors out with no lookup-by-name fallback.
- `descontoMaxPdv` (15%) isn't enforced and the discount field doesn't clamp — a fat-fingered 50% silently recalculates the total.
- "Gerar nota fiscal" is the lone CTA, irreversible, no summary; if the payment pill is wrong (defaults to PIX) the note issues anyway.

## Minor Observations

- The topbar prints the page title, then `PageHead` repeats a longer version of it immediately below — two H1-ish lines burning the top of the fold.
- The bell has a permanent unread dot and no click target; the calendar icon is inert; the topbar sliders icon duplicates the Configurações nav item.
- `statusTone` string-matching is fragile: `'Em análise '` carries a trailing space, and "Pronto para retirada" maps to `serious` (orange) — an order that's *ready* looks like a warning while "Entregue" looks positive.
- `preserveAspectRatio="none"` on the bar/area charts stretches bar corner radii and marker circles horizontally.
- `TierBadge` colours are hardcoded hex outside the token system (with a separate dark-mode block) — the one place token discipline breaks; app-source JSX otherwise has only 2 raw hex values total.
- `FormGrid` renders `<label>` as a sibling of the input, not associated (no `htmlFor`/`id`) — clicking the label doesn't focus the field and screen readers don't pair them.
- Number inputs for every discount/percentage rely on `Number(x)||0` with no clamp despite `min`/`max` attributes.
- The dark theme never redefines `--rail-*`, so the rail stays full crimson in dark mode (probably deliberate, worth a conscious call).
- Dashboard "atualizado às 11:32" is hardcoded and will contradict the live clock in the PDV timer.

## Questions to Consider

1. The app already knows whether the user is a cashier, pharmacist, manager or admin — so why is that a *pill on the dashboard* instead of the organizing principle for the whole shell (nav, landing screen, permitted actions)? What is "one console for everyone" costing each role in clarity?
2. The counter scene is interrupted, customer-waiting, mid-size screen. What if the **PDV were the home screen**, and everything else lived one keystroke away behind the search bar that currently does nothing?
3. Where is friction mismatched to stakes across the whole app — one unconfirmed click to approve a controlled prescription or issue a fiscal note, versus 16 fields to price a product — and what's the right unit of friction for each: a confirm, a checklist affirmation, a forced 3-second review, a co-sign?
4. Red is the brand, the primary action, the focus ring and the danger colour at once. If pure `#a11017` could keep exactly one of those jobs, which one — and what carries the other three?
5. Fourteen screens are the same `CrudPage` with different columns. Is that healthy consistency, or a sign that half the product is a spreadsheet with extra steps that staff would rather edit inline?
